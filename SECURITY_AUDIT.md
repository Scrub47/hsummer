### What was changed

`supabase/migrations/20270301120000_security_audit_v2.sql`

- Grants `EXECUTE` on `private.can_join_together_topic(text)` to `authenticated` only. The policy runs as that role. The function stays in the `private` schema, which is not in the Data API.
- Drops any `realtime.messages` policy whose check is exactly `true`.
- Drops and recreates `together_channel_read` and `together_channel_write` for `authenticated`, broadcast and presence only, when the caller is a contributor of that open session. No `ALTER TABLE`. No `SET ROLE`.
- Replaces `security_audit_gaps()` with the extra checks. `CREATE OR REPLACE` does not delete rows. The function is revoked from `public`, `anon`, and `authenticated`, then granted to `service_role` again, because a replace does not reset grants.

`src/lib/schedule/qstash.ts` passes the request URL into `Receiver.verify`. A signature for a different URL returns false.

`.github/workflows/ci.yml` and `db-backup.yml` pin checkout `11d5960a326750d5838078e36cf38b85af677262` (v4.4.0) and setup-node `49933ea5288caeca8642d1e84afbd3f7d6820020` (v4.4.0), set `permissions: contents: read`, and check the gitleaks tarball sha256 `79a3ab579b53f71efd634f3aaf7e04a0fa0cf206b7ed434638d1547a2470a66e` before installing it.

### Dashboard settings this SQL cannot change

- Realtime → Settings → turn **Allow public access** off. The app already joins with `private: true`. The switch is what stops a client that leaves that flag off.
- Authentication → Providers → leave Email (magic link) and Google on. Turn the email **password** provider off on the hosted project. This app never sets a password. Local tests still create passwords through the admin API.
- Authentication → Providers → Email → turn on leaked-password protection if the password provider is still on.
- Authentication → Rate Limits → leave the built-in limits on. The app's own limits do not see a direct call to `/auth/v1/otp`.
- Authentication → Bot and Abuse Protection → Turnstile, only after the site key, the Vercel secret, and this dashboard secret are all set. Leave all three empty until then.
- Authentication → URL configuration → redirect allow list is this site (and preview URLs you actually use), not `*`.
- Data API → exposed schemas stay `public` and `graphql_public`. Do not add `private`.
- MFA is for Isaac's Supabase and GitHub logins. The product has no password for members to attach a second factor to.

### Checked and left as they are

- Live Together frame uploads. `can_upload_booth_object` allows a solo frame and an open pass frame. It does not allow `mode = 'together'`, so a together JPEG is refused by storage. That is fail-closed, not a leak. Widening it was not part of this fix. If a strip never saves, the safe change is to allow the shot's owner only while that session's status is `capturing`, with the same path and size checks as a pass. Do not open the bucket.
- Push subscription keys stay plaintext. The server has to hand them to Web Push. The row is owner-only.
- HSTS is sent without `preload`.
- Turnstile stays optional until the three secrets exist.

## What Supabase may flag in the new migration

File: `supabase/migrations/20261207120000_security_hardening.sql`. Paste it once, as one script, before merging.

The SQL editor can mark `REVOKE` as destructive. These statements do not delete rows, policies, or buckets.

| Statement                                                                             | Why it is safe                                                                                                                                                                                                                                |
| ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `revoke insert` / `revoke update` on `public.push_subscriptions` from `authenticated` | Drops the wide table grant. The next statements grant insert and update back on `user_id, endpoint, p256dh, auth` only. Existing devices stay. The app's upsert still works. `id` and `created_at` keep their defaults.                       |
| `revoke all` on the new functions from `public`, `anon`, and `authenticated`          | Postgres grants `EXECUTE` to `PUBLIC` by default. Removing it does not drop the function. `service_role` is granted afterwards for `consume_auth_attempt` and `security_audit_gaps`. The trigger functions are only called by their triggers. |
| `enable row level security` on `private.auth_attempts` and `private.join_attempts`    | No policies, so the Data API cannot read them. The functions are `security definer` and run as the owner, which bypasses RLS unless it is forced. RLS is not forced, so redeem and the auth counter still insert.                             |

`CREATE TRIGGER` is not repeatable. If the script stops halfway, read the error before pasting it again. `CREATE OR REPLACE FUNCTION` is repeatable.

| `CREATE OR REPLACE FUNCTION private.memories_guard` | Replaces the function body so a finished Live Together strip can be saved the same way a pass strip is. It does not drop a table, column, policy, or row. Supabase may flag the replacement.    |
| `DELETE` inside `release_together_shots`            | Function body only. It does not run when the file is applied. After a Live Together upload fails, it deletes that caller's own `booth_shots` rows for that session. Other people's frames stay. |

`on delete cascade` appears only on the new foreign keys. Enabling RLS on `realtime.messages`, when that schema exists, does not delete messages.

## Encryption decision

Disk encryption is Supabase's. The app additionally hashes invite tokens and encrypts the weekly dump with GnuPG.

Push subscription keys are the one sensitive column that stays readable to the server. They are public keys and an auth secret in the Web Push sense, but they are only useful with the matching endpoint, and only the owner can select the row. Encrypting them with a key stored on Vercel would not hide them from the operator who can already decrypt the backup. Leaving them plaintext is the choice, not an oversight.
